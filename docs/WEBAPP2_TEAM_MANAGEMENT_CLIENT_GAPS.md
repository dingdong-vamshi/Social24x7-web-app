## Video-specific issues and minimal proposals

1. **Member-focused workflow:** old deployed app opens a member modal; prototype uses a dedicated member URL and Customer chats / Profile & access tabs; Partner spreads identity, metrics, editor and supervision over a long page. This can make the same actions hard to find. Propose a focused member view using existing RPCs, with summary cards and explicit navigation. No lifecycle rewrite required.
2. **Rich chat content and share tools:** live RPC result fields are `message_id,sender_id,body,message_kind,created_at,sender_type,sender_display_name,sender_tagline,representative_verified`. There is no typed attachment, product or order card payload. Both current and original Work repositories consume that contract. Copying the video UI alone cannot make authorized cards work. Propose typed, authorization-checked payloads + signed private media + share pickers. Requires backend/design approval. Never broaden Personal Chat access.
3. **Company feed/reels:** Partner's existing recovery already added product and post image/video rendering with safe bucket handling. The actual remaining difference is the video’s social-style actions/product tags/reels navigation, not absence of media. Decide whether employees can like/comment/share as the company and define that authority before implementation.
4. **Invitation permission timing:** video shows switches before creation. Old and current invite UIs choose a role; current lets owner edit individual overrides afterward. RPC already accepts `p_permissions`, so a reviewed UI-only optional override step could reuse it. Do not silently change Agent defaults or broaden grants.
5. **Identity preview/department:** video shows an explicit customer-facing preview and a department select; both old/current forms lack that preview and use free text. A preview must state “appears only after activation and approval”; suggested department choices may preserve custom text. These are UI improvements, not verification evidence.
6. **Domain and login format:** video says only a specific company email domain gets the tick and shows a login containing `@`. Actual original/current contract validates email syntax, not company-domain ownership; login format is 3–40 letters/numbers/dot/underscore/hyphen, not `@`. These are business-policy differences. Adding domain restrictions or changing identity normalization without a migration plan could lock out legitimate existing employees. Needs explicit policy decision and compatibility/security review.
7. **Verified badge:** original/video use a blue icon; Partner owner/history views use textual verified labels. Historical message verification is recorded attribution, not proof that a suspended representative retains current permission. Preserve that distinction in any badge change.
